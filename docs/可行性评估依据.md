# Kiloframe 项目可行性评估依据

> 来源：对公众号文章《Threejs性能优化 | WebGL场景加载1000个glb模型帧率是10帧，用meshletDrawingPipeline后是否能够提升到60》的可行性交叉核验
> 评估日期：2026-11-08 ｜ 可视化版本：`Three.js-meshlet-可行性评估.html`（同目录）

## 总体判定

**方向正确、结论稳妥、可执行；结论可信度 ≈ 8/10，技术事实准确度中上（需 3 处纠偏）。**

文章大方向正确：WebGL 原生不支持 Meshlet，不能"开开关"就从 10 帧到 60 帧；短期靠 InstancedMesh / 几何合并 / LOD / 剔除 / 资源压缩降 Draw Call，长期才谈 WebGPU 重构。

## 事实核实表

| 文章论断 | 判定 | 核验依据 |
|---|---|---|
| WebGL（含 2.0）原生不支持 Meshlet 渲染管线 | ✅ 正确 | Meshlet 依赖 Compute Shader + Indirect Draw，属 Vulkan/DX12/Metal/WebGPU 范畴；WebGL 无计算着色器 |
| 1000 个独立 GLB 至少 1000 次 Draw Call，CPU 成为瓶颈 | ⚠️ 部分正确 | Draw Call 过载是常见主因但非唯一；高面数/大纹理也会造成 GPU 填充率瓶颈。10 帧（100ms/帧）需先 profile 验证 |
| Meshlet 主要解决 GPU 端剔除与 LOD 过渡 | ✅ 正确 | 与业界对 Meshlet/Mesh Shader 用途认知一致 |
| 迁移到 WebGPU 可"引入 Meshlet 和 GPU Driven Rendering" | ❌ 过度乐观 | **WebGPU 核心规范目前没有网格着色器（Mesh Shader）阶段**。只能用 Compute Shader + 间接绘制实现 GPU 驱动渲染（近似收益），工程量大、未标准化 |
| InstancedMesh / 合并几何体可把 DrawCall 从 N 降为 1，从而 10→60 | ⚠️ 条件成立 | 仅当模型**几何相同**（实例化）或**异构但同材质且静态**（合并）才成立；不同复杂模型需 LOD+剔除兜底。文章自评"30-60 帧、取决于复杂度"是准确区间 |
| Draco/KTX2 压缩、纹理图集、关抗锯齿、降像素比等 | ✅ 正确 | 均为标准、无争议的最佳实践 |

## 三处必须修正的认知

1. **别把"WebGPU"和"Meshlet"划等号。** 现阶段 WebGPU 能做的是 GPU 驱动渲染（Compute Culling + Indirect Draw），不是网格着色器；真正的 Meshlet 未标准化，暂不具备落地条件。
2. **"10 帧 = CPU 瓶颈"不可先入为主。** 先用 `renderer.info.render.calls / triangles` 与 DevTools Performance 分辨 `Scripting`（JS 逻辑）与 `Render`（绘制）耗时，方案随诊断结果而定。
3. **60 帧不是保票。** 收益上限取决于 1000 个模型是否同构/同材质；异构高模场景收敛到"可接受"而非必然满帧。

## 方案评估矩阵

| 方案 | 可行性 | 预期收益 | 落地成本 | 适用前提 |
|---|---|---|---|---|
| 短期① InstancedMesh | 高 | DrawCall N→1，极大 | 低 | 几何相同的重复物体（树/路灯/库位） |
| 短期② 几何体合并 mergeGeometries | 高 | DrawCall N→1，极大 | 中 | 静态 + 同材质不同几何 |
| 短期③ LOD + 视锥/遮挡剔除 | 中 | 显著降 GPU 负载 | 中 | 远距离/不可见对象占比高 |
| 短期④ Draco + KTX2 + 纹理图集 | 高 | 加载快、显存省 | 低 | 通用、无副作用 |
| 短期⑤ 烘焙光照 / 关 MSAA / 降像素比 | 高 | 显著降片元负载 | 低-中 | 静态光影可预烘 |
| 长期⑥ 迁移 three-webgpu | 中 | 彻底解决海量物体 CPU 瓶颈 | **高（重构）** | 业务允许换渲染栈、长期演进 |
| 长期⑦ 真正的 Meshlet | 低 | —（暂不可得） | 极高 | WebGPU 网格阶段尚未标准化 |

## Kiloframe 演示项目落地路线

1. **定位瓶颈（必做）**：`renderer.info` 看 calls/triangles；DevTools Performance 分 `Scripting` / `Render`。结论决定后续手段取舍。
2. **按同质性分类**：相同几何 → InstancedMesh；同材质静态 → mergeGeometries；几何/材质各异 → LOD + 剔除组合，不硬合。
3. **资源瘦身**：GLB 走 Draco，纹理转 KTX2/BasisU，小纹理图集化，按屏幕占比分配分辨率。
4. **负载减压**：静态光影烘焙 Lightmap；仅 1 个主方向光投阴影；按需关 MSAA、降像素比；移除时 `dispose()` 几何/材质/纹理。
5. **决定是否升级（远期单独立项）**：业务允许换渲染栈才评估 three-webgpu + GPU 驱动渲染，按重构项目预算。

## 对 Kiloframe 的直接指导

- 演示核心叙事：**同一 1000 模型场景多模式对比**——基线（1000 独立 Mesh）vs InstancedMesh vs 几何合并 vs LOD+剔除。
- HUD 必须展示 `renderer.info`：Draw Calls、Triangles、FPS——正好验证"10 帧 = Draw Call 瓶颈"这一论断。
- 预期结论：同构场景 InstancedMesh 收益最大（N→1）；异构场景需组合拳，60 帧非保票。
